# SV300 RTOS 쓰레드 구조 분석

> 작성: 2026-09-23 · 대상: SV300 3채널 빌드(CH3, HWV1/HWV2)
> RTOS: **Keil RTX**(RL-ARM, CMSIS-RTOS v1 경유). 활성 포트 `common/os_port_rtx.c`.
>  · `__FREERTOS` 미정의 → 소스의 `#else`(os_evt_*/isr_evt_set) 경로가 실코드. `#ifdef __FREERTOS` 블록은 死코드.
>  · `WV_STAGED`/`WV_QCAP` 미정의 → 전 태스크 생성, Quiet-Capture(g_wfbQuiet 양보) 컴파일 제외.
> 목적: 태스크 구성·신호 배선·FS(flash) 접근 귀속 파악 + 통합 후보 도출.

---

## 0. 요약

- 정식운전 태스크 **16개** + CycloneTCP 웹서버 **~5개**(리스너1+커넥션4) ≈ 21개. RTX `OS_TASKCNT=30`.
- **스택 640워드(2560B) 일괄 강제**: `osCreateTask`(os_port_rtx.c:86-101)가 `stack==NULL`이면 `stackSize`를 무시하고 `os_tsk_create_ex`로 생성 → RTX `OS_STKSIZE=640`(RTX_Conf_CM.c:42)이 모든 태스크에 적용. **app_main.c의 `stackSize=256/512`는 死코드.** → 태스크 수 자체가 RAM 비용(태스크당 2.5KB).
- **우선순위 수치**(os_port_rtx.h:45-72): LLOW=1 < LOW=2 < NORMAL=3 < HIGH=4 < HHIGH=5 < REALTIME=6.
- **Meter0/Meter12(REALTIME)는 FS를 직접 만지지 않는다** — 실시간 캡처와 flash I/O가 설계상 격리됨.
- 통합 실익 큼: PostScan+RMSLog+Energy(3→1), Trend→FS 흡수. flash write 일원화로 XIP 정지 창구 최소화.

## 2. 역할·트리거·주기·공유데이터

### 신호 배선 (생산자 → 소비자)
- **ADE9000 IRQ → `meterIrqSvc(id)`**(ade9000.c:2580): M0 IRQ→`tid_meter[0]`, **M1/M2 IRQ→둘 다 `tid_meter[1]`**(단일 플래그 0x1). 라우팅 한 곳.
- `readWFB_Data` 파형 절반참 → `os_evt_set(0x1, tid_wave[0])`.
- `meter_scan` 이벤트별 notify: energy→`tid_energy`, post→`tid_post`(0x1/0x2/0x4), rmslog→`tid_rmslog`.
- FFT 기동: RTX 경로는 `copyFftData` 계열(meter.c:2452)의 `os_evt_set(0x1, tid_fft)`. (Wave_Task 끝의 tid_fft notify는 FreeRTOS 경로만; RTX는 주석)
- FS 요청: `putFsQ`→`os_evt_set(0x1, fsQ.tid)`. Cmd: `os_evt_set(0x8, cmdQ.tid)`.

## 3. FS(flash) 접근 귀속

**FS write 아키텍처 = 2부류:**
1. **비동기(큐 경유)** — `putFsQ()`→`fsQ` 링버퍼→**FS_task(LOW)**가 실제 fopen/fwrite. 생산자 비블로킹.
2. **동기(직접 호출)** — 함수 내부에서 곧바로 fopen/fwrite. 호출 태스크가 flash write/erase 동안 블로킹.

모든 flash W/E는 SPIFI `ProgramPage`/`EraseSector`(FS_SPIFI_FlashPrg.c)를 거치며 **`g_sdBusy=1`**(XIP 정지→M0 교란 표시). FRAM/EEPROM(`ChipEepWrite`/`storeEnergyNVR`)은 빠른 NVRAM이라 XIP 무관.

| 태스크 | FS 작업 | 방식 | 주기 | 느린 flash W/E |
|--------|---------|------|------|:---:|
| **Meter0/Meter12** (RT) | **없음**(init 시 initPQHeader만, 루프 前) | — | 부팅1회 | **아니오** |
| **PostScan** (HIGH) | 품질10m/주간, 알람상태, max/min | **직접** | 10분/알람변화/15분 | **예** |
| **Energy** (HIGH) | 에너지 시간/15분/월아카이브/디맨드 | **직접** | 1h/15m/일1회 | **예** |
| **Trend** (LOW) | 트렌드 레코드 append | **직접** | 1분 | **예** |
| **FS_task** (LOW) | 큐소비: 캡처/알람/이벤트/rm/로테이션+설정저장 | **직접(큐소비)** | 큐 도착시 | **예** |
| **Wave** (HHIGH) | 파형캡처 조립→`putFsQ` | 큐(비블로킹) | 이벤트시 | 아니오(위임) |
| **RMSLog** (HIGH) | RMS캡처 조립→`putFsQ` | 큐(비블로킹) | 이벤트시 | 아니오(위임) |
| **HTTP 스레드** | FW 업로드 write, 세션키(부팅1회) | 직접 | FW업로드시 | 예(업로드시) |
| IOM/FFT/SNTP/LED/CmdProc/Shell | 없음(명령은 플래그만) | — | — | 아니오 |
| **부팅 init**(태스크 前, 직렬) | 마운트·설정/에너지/알람/이벤트 로드 | 직접 | 부팅1회 | 예 |

**핵심 호출체인(직접 flash write):**
- `PostScan_Task`→`calcRmsAngle`(ade9000.c:1715)→`updateQualData`(Quality.c:852)→`appendQualLog`/`updateQualWeekData`(fopen/fwrite)
- `Energy_Task`→`energy_scan`→`storeEnergyLog*Fs`/`archiveEnergyLog15Day`/`storeDemand`(fopen/fwrite)
- `Trend_Task`→`appendTrendRcrd`(meter.c:1355, fopen/fwrite)

**명령→플래그→소비 태스크**: Modbus/CmdProc는 `saveSetting`/`factReset`/`rstDemand`/`rstMaxMin` **플래그만** 설정. 실제 write는 소비 태스크: 설정저장→FS_task, rstMaxMin→PostScan, rstDemand→Energy.

**결론**: 느린 flash write(XIP 정지)를 직접 하는 태스크 = **PostScan/Energy/Trend/FS_task(+FW업로드 HTTP)**, 모두 Meter(REALTIME)보다 저우선. Meter는 FS 프리미티브를 전혀 호출 안 함. 간섭 경로는 "FS 직접 접근"이 아니라 **동일 SPIFI flash의 program/erase에 의한 XIP 정지**(g_sdBusy). `WV_QCAP`(현재 컴파일 제외)이 이를 겨냥한 완화책이었음.

## 4. 통합 후보 분석

### ⭐ 후보 A: PostScan + RMSLog + Energy (3→1) — 최우선 권장
- **근거**: 셋 다 **HIGH** + `meter_scan`이 깨우는 소비자 + 순수 CPU 계산(짧음). 트리거·주기(100ms~1초) 동일 계열.
- **이점**: RAM ~5KB(640워드×2), HIGH 컨텍스트스위칭 2건↓, `meter[]` 접근 직렬화(경합↓).
- **설계**: 통합 루프에서 분주 — 1/2cycle RMS(빠름) + 1초 계산/알람/에너지(느림). **flash write는 FS 큐로 위임**.
- **위험**: RMSLog의 `g_meterReady` 게이트(부팅 통신개방)와 Energy 15분 아카이브를 한 루프에 묶으므로 분주 정확성 필수.

### 후보 B: Trend → FS 큐 흡수 (태스크 제거)
- Trend(LOW)는 1분마다 flash append만 → FS_task가 처리(Trend를 FS 큐 생산자로 강등).
- **이점**: RAM 2.5KB + 저우선 flash 접근 단일화.
- **위험**: Trend 1분 폴링이 FS 100ms 반응성 저해 금지 → "1분마다 trend append"를 FS 큐 작업으로.

### 후보 E(선택): SNTP → 저부하 폴러 흡수. 이득 작음, 후순위.

### ❌ 통합 금지
| 태스크 | 이유 |
|--------|------|
| **Meter0/Meter12** | REALTIME 버스별(SSP0/SSP1) 실시간 캡처. 합치면 한 버스 대기가 다른 버스 캡처 막아 파형 seam. **리팩토링 핵심 성과** |
| **FFT** | Goertzel ~1.4초 블로킹(LLOW). 상위 결합 시 초 단위 블로킹 |
| **FS** | 블로킹 flash I/O를 LOW로 격리. **다른 걸 FS로 흡수는 OK, FS를 상위와 합치면 블로킹 전파** |
| **LED** | taskMonitor()로 전 태스크 WDT clear. 죽으면 시스템 리셋 |
| **IOM** | 1ms tight-loop. HIGH 계산을 1ms마다 방해 |
| **IpScan/Proxy** | 블로킹 소켓 accept/recv. select 다중화 없인 통합 불가 |

## 5. 통합의 핵심 가치 — flash write 일원화

**현재**: 느린 flash write(XIP 정지)가 **5곳** 분산 — 동기 PostScan/Energy/Trend(3곳 산발) + 큐 Wave/RMSLog→FS_task.

**통합 후(A+B)**: 모든 flash write가 **FS_task 한 곳**으로 집중(+FW업로드 HTTP만 예외).
- XIP 정지가 단일 저우선 태스크에서만 발생 → 실시간 Meter 캡처 간섭 창구 최소화
- g_sdBusy/WV_QCAP 관리 단순화 (또는 불필요)

---

## 6. 리팩토링 우선순위

1. **(高)** 후보 A: PostScan+RMSLog+Energy 통합 + flash write FS 큐 위임 — RAM/스위칭 이득 최대, flash 간섭 일원화.
2. **(中)** 후보 B: Trend를 FS 큐로 흡수 — flash 접근 단일화.
3. **(低)** 후보 E: SNTP 정리 — 이득 작음.

**RAM 이득 계산**: 태스크당 2560B 고정 강제 → A안 −2개 ≈ 5KB, B안 −1개 ≈ 2.5KB, 합 ~7.5KB + OS_TASKCNT=30 여유 확보.

**주의**: 통합은 3개 태스크 로직 병합 + 분주 + flash write 큐 전환으로 적지 않은 리팩토링. 현재 진행분(버스별 분리 + 진단 + FS 16MB) 커밋·안정화 후 별도 단계로 진행 권장.
