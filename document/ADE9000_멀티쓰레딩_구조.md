> 범위: ADE9000 에너지 계측 IC 3개(M0/M1/M2)를 둘러싼 태스크·인터럽트·SSP 버스 락 구조 + 3-스레드 동시성/충돌 분석

## 0. 빌드 구성

`keil/SV300_app.uvproj`가 **`HWV1` + `CH3`** 를 정의한다.
- `HWV1` → 아래 모든 `#ifdef HWV1` 락 코드가 실제로 컴파일된다.
- `CH3` → 3칩(M0/M1/M2) 토폴로지가 활성화된다.
- **RTOS는 RTX(Keil RTX / CMSIS-RTOS v1)** 이다. `os_port_config.h:34`에서 **`USE_RTX`** 를 정의하고 `USE_FREERTOS`는 주석 처리(`:33`)돼 있다.
  - 따라서 소스에 보이는 `#ifdef __FREERTOS` 블록(`xTaskNotifyWait`/`xTaskNotifyFromISR`/`xSemaphore*`)은 **컴파일되지 않는 죽은 경로**다. 실제 live 신호 경로는 RTX의 `os_evt_wait_*` / `isr_evt_set` / `os_evt_set` 이다.
  - Tick = 1ms, CPU 204MHz, 라운드로빈 OFF (`RTX_Conf_CM.c`).

> ⚠️ **스택 크기 주의**: 모든 앱 태스크는 `osCreateTask`에 `stack=NULL`을 넘기므로, RTX 포트(`common/os_port_rtx.c:92-101`)가 요청한 `stackSize`를 **무시하고 고정 `OS_STKSIZE = 640워드(2560B)`** 를 모든 태스크에 적용한다. 아래 표의 스택 값은 코드상 "요청값"일 뿐 실제 할당값이 아니다. (근거 주석: `RTX_Conf_CM.c:42`, `net_config.h:197`)

## 1. 큰 그림 — IRQ 구동형 이벤트 아키텍처

ADE9000 계측은 **폴링이 아니라 인터럽트 구동**이다. 각 칩의 IRQ0 핀 → GPIO 핀 인터럽트 → 해당 Meter 태스크 알림 → 태스크가 `STATUS0/STATUS1`을 읽어 이벤트별로 분기 처리한다.

```
 ADE9000 M0 (IRQ0) ──> PIN_INT0_IRQHandler ──> meterIrqSvc(0) ──notify 0x1──> Meter0_Task ─> meter_scan(0)
 ADE9000 M1 (IRQ0) ──> PIN_INT1_IRQHandler ──> meterIrqSvc(1) ──notify 0x1──> Meter1_Task ─> meter_scan_2(1)
 ADE9000 M2 (IRQ0) ──> PIN_INT2_IRQHandler ──> meterIrqSvc(2) ──notify 0x1──> Meter2_Task ─> meter_scan_2(2)
```

- **ISR** (`ade9000.c:2412-2447`): `meterIrqSvc()`는 RTX 경로에서 `isr_evt_set(0x1, tid_meter[id])`로 해당 Meter 태스크에 이벤트 플래그 `0x1`만 세우고 즉시 반환한다. **ISR 안에서는 SPI 접근을 전혀 하지 않는다.**
- **태스크**: `os_evt_wait_and(0x1, 20)` (M0, 20ms 타임아웃) / `os_evt_wait_and(0x1, 50)` (M1/M2)로 ZX(영점교차) 알림을 대기한 뒤, **실제 SPI 읽기는 모두 태스크 컨텍스트**에서 수행한다.
- ISR→태스크 매핑: `PIN_INT0/1/2_IRQHandler`가 각각 `meterIrqSvc(0/1/2)` 호출. M2 핸들러는 `#if defined(CH3) && !defined(CH1)` 로 조건부.

### Meter 태스크 진입 시퀀스 (`meter.c:5177~`)

각 Meter 태스크는 다음 순서로 초기화 후 무한 스캔 루프에 진입한다.
1. `wQ[id]` 파형 링버퍼 초기화(`memset`)
2. `initADE9000(id)` — SPI 실패 시 5초 간격 재시도 루프(`getAdeStatus(id)->online` 대기)

5. `_enableTaskMonitor(...)` — 워치독 감시 등록
6. `while(1) { meter_scan(id) 또는 meter_scan_2(id) }`

## 3. `meter_scan` vs `meter_scan_2` — M0와 M1/M2의 차이

### M0 = `meter_scan` (`ade9000.c:2910`)
STATUS0 이벤트를 매 인터럽트마다 **전부 처리**. ZX 대기 타임아웃 20ms.

STATUS0 비트별 처리:
- bit0  → `readEnergy` (Energy READY, 1s 주기)
- bit17 → `readWFB_Data` (WaveForm Buffer page-full)
- bit19 → `readPeriod` + `readPhaseFastRMS` + `checkPqEvent` (RMS 1/2 cycle)
- bit20 → `readRmsAngle` (RMS 10/12 cycle)
- bit18 → `readPhasePower` (PWR_READY, 1s)
- bit21 → `readPhaseTHD`
- bit25 → `readTemp`

### M1/M2 = `meter_scan_2` (`ade9000.c:2767`)
SSP1 공유 부하 분산을 위해 무거운 PQM 읽기를 분산한다. ZX 대기 타임아웃 50ms(RR·슬라이스·mutex 여유).

- **라운드로빈** (`m12_pq_rr_owner`): 무거운 PQM(period/RMS/THD)은 M1↔M2 번갈아 한쪽만 (`ade9000.c:2822-2842`)
- **슬라이스** (`m12_pq_slice`): bit19(period+FastRMS)와 bit21(THD)을 인터럽트마다 번갈아 (`:2827-2838`)
- **예외**: WFB(bit17)와 Energy(bit0)는 연속성이 필요해 RR과 무관하게 매번 처리 (`:2808-2819`).
  - 과거에는 RR+슬라이스로 WFB를 ~1/6만 읽어 M1/M2 파형이 깨졌음 → 지금은 매 page-full마다 읽음.

### 공통 안전장치 — STATUS0 조기 ack
STATUS0를 **처리 전에** `write_reg32(STATUS0)`로 조기 클리어하고 로컬 스냅샷(`stat0_snap`)으로 처리한다. 긴 스캔(풀 PQM) 도중 새로 뜬 WFB page-full(bit17)까지 함께 지워져 그 절반을 건너뛰어 파형 seam(불연속)이 생기는 것을 방지한다. (`ade9000.c:2803-2805`, `:2959-2962`)

## 3.5. 태스크 파이프라인 — 누가 누구를 깨우는가 (RTX 이벤트 플래그)

Meter 태스크가 STATUS0 비트별로 데이터를 읽은 뒤, 해당 소비자 태스크에 RTX 이벤트 플래그를 세워(`os_evt_set`) 파이프라인을 흘려보낸다.

```
 ADE9000 IRQ0 ─(ISR isr_evt_set 0x1)→ Meter0/1/2_Task ─┬─ readWFB_Data      ─(0x1)→ Wave_Task ─(notify 0x1)→ FFT_Task
                                                        ├─ readEnergy        ─(0x1)→ Energy_Task
                                                        ├─ readPhaseFastRMS  ─(0x1)→ RMSLog_Task
                                                        ├─ readRmsAngle      ─(0x1)→ PostScan_Task
                                                        ├─ readPhasePower    ─(0x2)→ PostScan_Task
                                                        └─ readPhaseTHD      ─(0x4)→ PostScan_Task

 SPI-DMA RX 완료 ─(ISR isr_evt_set 0x10)→ 전송을 요청한 태스크(t_meter[chn])
```

| 생산자 (파일:라인) | 트리거 | 신호 | 깨우는 태스크 | 대기 방식 |
|---|---|---|---|---|
| `meterIrqSvc` `ade9000.c:2421` | ADE9000 IRQ0(ISR) | evt `0x1` | **Meter0/1/2** (`tid_meter[id]`) | `os_evt_wait_and(0x1, 20/50)` |
| `readWFB_Data` `ade9000.c:2080` | WFB half full | evt `0x1` | **Wave_Task** (`tid_wave[id]`) | `os_evt_wait_and(0x1, 0xffff)` |
| `readEnergy` `ade9000.c:1184` | EGY_RDY(~1s) | evt `0x1` | **Energy_Task** (`tid_energy`) | `os_evt_wait_and(0x1, ...)` |
| `readPhaseFastRMS` `ade9000.c:1561` | 반주기 RMS 창 full | evt `0x1` | **RMSLog_Task** (`tid_rmslog`) | `os_evt_wait_and(0x1, ...)` |
| `readRmsAngle` `ade9000.c:1632` | 10/12주기 RMS | evt `0x1` | **PostScan_Task** (`tid_post`) | `os_evt_wait_or(0xf, 100)` |
| `readPhasePower` `ade9000.c:1308` | PWR_RDY(~1s) | evt `0x2` | **PostScan_Task** | (동일, OR 대기) |
| `readPhaseTHD` `ade9000.c:1102` | THD_PF ready | evt `0x4` | **PostScan_Task** | (동일, OR 대기) |
| `Wave_Task` `meter.c:2621` | 파형 윈도 처리 완료 | notify/evt `0x1` | **FFT_Task** (`tid_fft`) | `os_evt_wait_and(0x1, 0xffff)` |

- **PostScan_Task**는 세 플래그(0x1 RMS-angle, 0x2 Power, 0x4 THD)를 `os_evt_wait_or(0xf, 100ms)`로 OR 대기하며, 세워진 플래그에 따라 `calcRmsAngle`/`calcPower`+알람/`calcTHD`를 수행하고 `publishMeterSnap(id)`로 Modbus·웹용 스냅샷을 원자적으로 발행한다.
- **RMSLog_Task**가 `g_meterReady`를 세워야 웹/Modbus가 데이터를 서빙한다(`app_main.c:683-684`).
- **`t_meter[2]`** (`ssplib.c:24`)는 DMA 완료 통보 대상으로, 매 SPI-DMA 전송 시 `os_tsk_self()`로 현재 태스크로 갱신된다(`ssplib.c:261`). 이는 Meter 태스크 알림용 `tid_meter[]`와 별개다.

## 4. SSP(SPI) 버스 공유와 락 모델 (`ssplib.c`)

### 버스 매핑 (`ssplib.c:16, 42-45`)
```c
static LPC_SSP_T* _sspBase[] = {LPC_SSP0, LPC_SSP1};
static uint8_t meterToSspBus(uint8_t mid) { return (mid == 0) ? 0 : 1; }
```
- **M0 → SSP0 (bus 0, 전용)** → 락 불필요
- **M1, M2 → SSP1 (bus 1, 공유)** → `ssp1_mutex`로 직렬화

### 락 프리미티브
| 이름 | 종류 | 선언 | 생성 | 역할 |
|---|---|---|---|---|
| `ssp1_mutex` | mutex | `ssplib.c:28` | `:190` | SSP1 기본 버스 락 (M1/M2 모든 접근 직렬화) |
| `ssp1_wfb_mutex` | mutex | `ssplib.c:31` | `:191` | 버스트 외부 락 (상대 미터의 WFB 읽기 배제) |
| `ssp1_burst` | volatile flag | `ssplib.c:215` | — | 재귀 취득 회피 플래그 (락 아님) |
| `ssp_dma_sem[2]` | binary sem | `ssplib.c:38` | `:194-195` | DMA 완료 신호(버스 중재 아님, FreeRTOS 전용) |

- **`taskENTER_CRITICAL`/`__disable_irq`로 SSP를 보호하지 않는다.** (`meter.c:146`의 유일한 `__disable_irq`는 파일시스템 큐 `fsQ` 보호용이며 SSP와 무관)
- SSP0(M0)에는 **mutex가 전혀 없다** — 모든 락은 `if (bus == 1)`로 게이팅된다.

### 표준 트랜잭션 패턴 (레지스터 접근 함수 공통)
```c
if (bus == 1) osAcquireMutex(&ssp1_mutex);
selectMeter(mid);          // 해당 칩 CS Low
spiIO8_Polling(...);       // 또는 spiIO_DMA
deSelectMeter(mid);        // CS High
if (bus == 1) osReleaseMutex(&ssp1_mutex);
```
적용 함수: `read_reg16`(`:577`), `read_reg32`(`:599`), `write_reg16`(`:645`), `write_reg32`(`:670`), `dma_read32n`(`:508`).
→ **모든 함수가 내부에서 락을 잡으므로 호출자는 락을 잡지 않는다(그리고 잡아서도 안 된다).**

### 칩셀렉트(CS)는 하드웨어 SSEL이 아니라 per-meter GPIO
CS 테이블 (`board.c:492-496`, CH3 빌드):
- M0_CS = GPIO7_16, M1_CS = GPIO3_8, M2_CS = GPIO5_15
- `selectMeter(id)` → GPIO Low (`board.c:1451-1453`), `deSelectMeter(id)` → GPIO High (`:1455-1457`)
- HWV1에서 `SSP_SSEL_Mode()`는 `id>0`이면 조기 반환(`board.c:1369-1373`) → M1/M2는 SSEL 핀먹스를 GPIO로 두고 CS를 순수 소프트웨어로 제어한다. M0(SSP0)만 SSEL 핀을 AUTO/MANUAL 먹스로 전환.
- SSP1에서 CS 토글은 **`ssp1_mutex` 보유 구간 안에서** 일어나므로 공유 MISO가 두 칩에 의해 동시에 구동되지 않는다.

### 죽은 코드
`read_reg32n`, `dma_read16/32`, `dma_write16/32`는 프로토타입만 있고 구현은 주석 처리됨. **실제 live한 DMA 함수는 `dma_read32n` 하나뿐**이다.

### DMA 완료 신호 (버스 중재와 별개)
`spiIO_DMA`(`ssplib.c:240-308`)는 mutex 작업을 전혀 하지 않고 GPDMA 채널 2개(Tx/Rx)를 킥한 뒤 RX 완료를 대기한다. 이는 **버스 소유권 락이 아니라 완료 신호**다.
- **RTX(현재 활성)**: `DMA_IRQHandler`(`ssplib.c:131-169`)가 RX 완료 시 이벤트 플래그 `0x10`을 전송 요청 태스크 `t_meter[chn]`에 세운다(`:148` chn0, `:161` chn1). `spiIO_DMA`는 `os_evt_wait_and(0x10, 100)`(`:298`)로 100ms 타임아웃 대기.
- FreeRTOS(죽은 경로): `ssp_dma_sem[chn]` 바이너리 세마포어 `xSemaphoreGiveFromISR`(`:146,159`) / `xSemaphoreTake`(`:291`) — 컴파일되지 않음.
- 타임아웃 시 stuck DMA 채널을 강제 종료하고 FIFO를 비운다.

## 5. 파형 버스트 락 (핵심 동시성 이슈) — `ssplib.c:199-237`

가장 정교한 부분이며, 실제 하드웨어 버그(단일 스파이크 → THD 오계측) 대응으로 진화했다.

### 과거 버그
종전에는 `dma_read32n`이 **페이지 단위**로 `ssp1_mutex`를 잡았다 놓았다. WFB page-full 시 8페이지를 연속 읽는데, 페이지와 페이지 사이 틈으로 상대 미터의 폴링 읽기(STATUS/RMS/Power, `read_reg*`/`write_reg*`)가 끼어들어 SSP1 클럭·상대 CS가 토글됐다. 이 활동이 ADE9000 동시 변환을 교란해 **버스트당 ~1샘플 손상(단일 스파이크)** 을 유발했고, 고조파는 `mag[h]/mag[1]` 정규화라 큰 임펄스가 하나만 섞여도 전 차수가 같은 크기가 되어 **THD/고조파가 100% 부근으로 뭉갰다.**

### 수정 — 2중 락 + 버스트 플래그
`readWFB_Data`(`ade9000.c:2022-2086`)가 8페이지 루프 전체를 `ssp1WfbLock`/`ssp1WfbUnlock`으로 감싼다. (호출: `:2041`, `:2086`)

```c
void ssp1WfbLock(uint8_t bus) {
    if (bus == 1) {
        osAcquireMutex(&ssp1_wfb_mutex);  // 상대 미터의 readWFB 배제
        osAcquireMutex(&ssp1_mutex);      // 버스트 ~2.4ms 동안 SSP1 독점
        ssp1_burst = 1;                   // 재귀 취득 회피 플래그
    }
}
void ssp1WfbUnlock(uint8_t bus) {
    if (bus == 1) {
        ssp1_burst = 0;
        osReleaseMutex(&ssp1_mutex);
        osReleaseMutex(&ssp1_wfb_mutex);
    }
}
```
- **`ssp1_burst` 플래그**로 `dma_read32n` 내부에서 `ssp1_mutex`를 재취득하지 않도록 함 (`if (!ssp1_burst) osAcquireMutex(...)`, `ssplib.c:522/534`) → 자기 자신과의 데드락/재귀 취득 방지.
- **락 세분성 변화**: 일반 `dma_read32n`은 페이지당 grab/release, 버스트는 8페이지 전체를 한 번의 보유로 묶음.

### 무엇을 / 얼마나 / 누구를 막는가
- **잠금 대상**: 8페이지 버스트(~2.4ms) 동안 SSP1 버스 전체를 독점.
- **차단 대상**: (a) 상대 미터의 `readWFB`(via `ssp1_wfb_mutex`), (b) 상대 미터의 일반 폴링 레지스터 읽기/쓰기(`read_reg*`/`write_reg*`/`dma_read32n`, 모두 `ssp1_mutex` 경합).
- **여유**: 상대 미터는 최대 ~2.4ms 대기 → page-full 주기 16ms 안이므로 충분.
- **데드락 없음**: `ssp1_mutex`를 먼저 잡고 `ssp1_wfb_mutex`를 잡는 경로가 없어 락 순서 역전이 발생하지 않음. M0(bus 0)에서는 두 함수 모두 no-op.
- `readWFB_Data`는 버스트 전후로 `SSP_SSEL_Mode(id,1)`(`ade9000.c:2042`)/`SSP_SSEL_Mode(id,0)`(`:2085`)도 호출.

## 5.5. 3-스레드 동시성/충돌 분석

Meter0/1/2 세 스레드가 동시 실행될 때의 공유 자원 경합을 전수 조사한 결과다.

### 판정 요약표

| 대상 | 판정 | 근거 |
|---|---|---|
| **SSP0 (M0 전용)** | ✅ 안전 | M0 단독 사용, 경합 없음 |
| **SSP1 (M1/M2 공유)** | ✅ 안전 | `ssp1_mutex`로 전 접근 직렬화, CS는 락 내부 토글 (`ssplib.c:585,608,657,681,522`) |
| `read/write_reg*` tb/rb | ✅ 안전 | **스택 로컬** `tb[8/10]`/`rb[]` — 태스크별 격리 (`ssplib.c:578,601,647,672`) |
| `_tb[mid]`/`_rb[mid]` DMA 버퍼 | ✅ 안전 | per-meter 정적 배열 `[3][520]` (`ssplib.c:19`) |
| `t_meter[2]`, `isDma*[2]` | ⚠️ **규약 의존(취약)** | `chn`(버스) 인덱싱. M1/M2가 `t_meter[1]` 공유. DMA 설정~완료 대기가 `ssp1_mutex` 안이라 현재는 안전하나, **락이 `spiIO_DMA` 밖(`dma_read32n`)에 있어 규약 위반 시 즉시 완료신호 오배달** (§DMA setup 취약점) |

| `m12_pq_slice[]` | ✅ 안전 | per-id 인덱싱 (`ade9000.c:2762`) |
| `zxTimer` | — | 미존재. 관련 상태는 `meter[id].cntl.zxMonCnt` per-id |
| 소비자 wake (Wave/Energy/RMSLog/PostScan/FFT) | ✅ 안전 | 이벤트는 깨우기용, 실제 처리는 **per-id 플래그 폴링 루프**(§3.5 상세) |
| `ade9000[]`, `wQ[]`, `wbFFT8k[]`, `egy15[]` 등 대형 버퍼 | ✅ 안전 | 전부 per-id 배열, 더블버퍼 인덱스도 per-id |
| `pFFT`(fftMem), Goertzel 작업버퍼 `g_gz*` | ✅ 안전(단일스레드) | 채널 분리는 아니지만 **유일 호출자가 FFT_Task 하나** (`fft_radix2_czt.c:503-633`) |
| initPQHeader / 런타임 FS | ✅ 안전 | M0에서 m0→m1→m2 직렬 호출 + `fsFileMutex` (`meter.c:5262-5266`) |
| initADE9000 | ✅ 안전 | per-id 상태 + 레지스터 단위 `ssp1_mutex`. 시퀀스 인터리브돼도 CS로 칩 분리 |
| **`m12_pq_rr_owner`** | ⚠️ **benign data race** | M1↔M2 공유 단일 static의 RMW가 `ssp1_mutex` **밖** (`ade9000.c:2764,2822,2841`). race는 존재하나 무결성 무영향 |
| `meter[id].maxmin.fr` | ⚠️ **benign data race** | FFT_Task와 PostScan_Task가 동일 id를 락 없이 갱신(소비자-소비자, 3-미터 경합은 아님) |

### 핵심 결론 — "무결성은 안전, 그러나 취약(fragile)"

정확한 표현이 중요하다. 두 층위를 구분해야 한다:
- **데이터 무결성**(버스 손상·메모리 손상·데이터 유실) → ✅ 현재 안전.
- **data race의 유무** → ❌ **존재한다.** `m12_pq_rr_owner`·`maxmin.fr`는 락 없는 공유 RMW로 언어·메모리모델상 명백한 data race다. 다만 그 race가 무결성을 훼손하지 않는 **benign(무해) race**일 뿐이다.
- **견고성** → ⚠️ **취약하다.** 안전이 "코드로 강제된 격리"가 아니라 **깨지기 쉬운 규약(convention)** 에 의존한다.

안전을 떠받치는 두 축:
1. **버스 분리 + `ssp1_mutex` 직렬화** — M0는 전용 버스, M1/M2는 mutex로 SSP1 배타 접근. `t_meter[1]`·`isDma*[1]`·`ssp1_burst`도 이 mutex가 **간접** 보호한다. → 이 "간접 보호"가 취약점의 핵심: 락은 `dma_read32n`/`read_reg*`에 있고 `spiIO_DMA` 자신은 무방비이므로, 락 없이 SSP1을 치는 경로가 하나만 추가돼도 붕괴한다.
2. **소비자의 per-id 폴링 설계** — 이벤트 플래그는 "깨우기"용이고 실제 데이터는 per-id 더블버퍼(`efr/ere`, `fr/re`)에 실린다. RTX 이벤트 플래그 coalescing으로 wake가 유실돼도 소비자가 전 채널을 재스캔하므로 **데이터 유실·채널 혼동이 없다**. (이 축은 견고함)

### 취약점 목록

benign race 2건 + 규약 의존 취약점 1건(DMA setup) + 가정 의존 2건.

**① `m12_pq_rr_owner` — 락 없는 M1↔M2 라운드로빈 소유권 (benign race)** (`ade9000.c:2764`)
`meter_scan_2`에서 `if (id != m12_pq_rr_owner) {생략} else { …PQM처리…; m12_pq_rr_owner = (id==1)?2:1; }` (`:2822-2843`). 이 read-modify-write가 `ssp1_mutex` 밖이다.
- **race 존재**: 두 스레드가 락 없이 공유 변수를 RMW → 명백한 data race.
- **왜 무해한가**: `uint8_t` 단일 바이트라 값 tearing 없음. 쓰는 값이 항상 1 또는 2뿐이라 **owner가 0 같은 무효값으로 갈 경로가 없어 영구교착 불가**. 최악은 PQM(period/RMS/THD)이 한 라운드 skip/중복되는 것뿐 — 버스는 `ssp1_mutex`로 보호되어 손상 없고, 다음 인터럽트(수십 ms)에 자기교정.
- **견고화**: owner 갱신을 mutex 안으로 넣거나, 각 미터가 인터럽트 카운터 홀짝으로 독립 판단하게 바꾸면 공유 상태 자체가 소멸.

**② `meter[id].maxmin.fr` — 소비자-소비자 benign race** (`ade9000.c:1408,1918` vs `meter.c:1357`)
FFT_Task와 PostScan_Task가 동일 id의 `maxmin.fr`를 락 없이 증가시키고, PostScan이 `fr!=re`로 flash 저장 트리거. Meter 3-스레드 경합은 아니며, 최악은 극값 flash 저장 타이밍이 흔들리는 정도.

**③ DMA setup 동시성 — 규약 의존 취약점 (가장 위험)** (`ssplib.c:240,261,131-169`)
`spiIO_DMA`의 setup 시퀀스(완료플래그 리셋 → `t_meter[chn]` 설정 → GPDMA 채널 재설정 → SSP DMA enable → `os_evt_wait(0x10)`)는 **비원자적이고 그 자신은 락이 전혀 없다.** 안전은 오직 호출자(`dma_read32n`)가 `ssp1_mutex`를 잡는다는 규약에 달렸다.
- **버스 채널(SSP0/SSP1)로만 격리**: `dmaChTx/Rx[chn]`·`isDma*[chn]`·`t_meter[chn]`이 전부 `chn`(0/1) 인덱싱. M0(chn0)와 M1/M2(chn1)는 다른 채널이라 안전.
- **위험 = 같은 채널(chn1) 내 M1↔M2 겹침**: 규약이 깨져 M1 DMA 중 M2가 `spiIO_DMA`에 진입하면 → ⓐ 같은 GPDMA 채널(`dmaChTx/Rx[1]`) 재설정으로 M1 진행 전송 파괴, ⓑ `t_meter[1]`을 M2로 덮어써 **M1의 완료신호(0x10)가 M2로 오배달**(M1은 100ms 타임아웃, M2는 조기깨움), ⓒ 버스 데이터 손상. **= 파형 깨짐의 잠재 경로**.
- **현재는 `ssp1_mutex`가 이 겹침을 막지만**, 락이 `spiIO_DMA` 밖에 있어 "SSP1 접근은 항상 락 보유"라는 규약에 전적으로 의존. 락 실수 하나에 무너지는 구조.
- **참고 — gems7100 대조**: 자매 프로젝트 gems7100은 같은 `spiIO_DMA`에서 `if (t_meter[chn] == 0) t_meter[chn] = os_tsk_self();`로 **최초 1회만 설정(덮어쓰기 금지)** 하는 가드를 둔다(SV300은 매번 덮어씀). ⚠️ **정정**: gems7100의 동시성 안전은 **미터별 전용 버스(M0=SSP0, M1=SSP1, 칩:버스 1:1)** 에서 나온다 — 각 칩이 전용 버스라 애초에 경합이 없어 **SSP 락도 없다**. gems7100이 통합한 `Wave_task`(git `de56f36`)는 소비(파형 후처리) 태스크로, **경합 해결이 아니라 코드 단순화**다(Meter 스레드는 듀얼 시 2개 유지). SV300은 3칩/2버스라 M1·M2가 SSP1을 공유 → gems7100식 "칩당 전용 버스"가 HW상 불가능 → 버스별 스레드 분리가 필요한 이유.

### 가정 의존 취약점 (현재 안전하나 전제가 깨지면 붕괴)

- **불변식 A(SSP1 락)**: *"SSP1에 대한 모든 DMA/폴링 접근은 반드시 `ssp1_mutex`(또는 버스트 락)를 보유한 채"* — 깨지면 위 ③ⓐ~ⓒ가 즉시 발생.
- **불변식 B(FFT 단일 스레드)**: `pFFT`/`g_gz*` 작업버퍼는 채널 분리가 아니라 "FFT_Task가 유일 호출자"라는 전제로만 안전. FFT를 채널 병렬화하면 즉시 data race.

### ⚠️ 실환경 파형 손상과의 연관

이 문서 작성 시점(26/09) 실환경에서 파형 손상이 보고됨. 위 취약점 중 **③(DMA setup)** 과 **§5의 SSP1 버스트 락(26/09/10 "실기 검증 필요")** 이 유력 후보다. 파형(WFB)은 **유일하게 DMA를 쓰는 경로**(`dma_read32n`, `ade9000.c:2048`)이자 데드라인이 빡빡(page-full 후 16ms 내)해, 폴링과 성격이 근본적으로 다르다. 손상 채널·양상(M0만/M1·M2만/셋다, 스파이크/seam/THD)에 따라 원인이 갈리므로 §5.7 참고.

## 5.6. 단일 스레드 전환의 장단점

세 칩을 한 스레드가 순차 처리하는 방식으로 바꿨을 때의 손익. §5.5 취약점 대부분이 이 전환으로 **구조적으로 소멸**한다.

### 장점

| 이점 | 설명 |
|---|---|
| **동시성 취약점 원천 제거** ★ | `ssp1_mutex`·`ssp1_wfb_mutex`·`ssp1_burst`·RR·슬라이스 전부 불필요. §5.5의 benign race(①②)와 DMA setup 취약점(③)이 "끼어들 상대 스레드"가 없어 소멸 |
| **파형 손상 근본 처방** | 26/09/10 스파이크 원인("버스트 중 상대 미터가 끼어듦")이 구조적으로 불가능. `spiIO_DMA`가 락 없이도 안전해짐 |
| **코드 단순화** | 락 3종·RR·슬라이스·수동 직렬화(initPQHeader)·`t_meter[]` 배열이 전부 제거 가능 |
| **대조 사례 존재** | gems7100은 미터별 전용 버스(칩:버스 1:1)라 락 없이 경합 무 — SV300은 버스 공유라 다름. gems7100 Wave 통합은 소비 단순화지 동시성 처방 아님 |

### 단점 / 리스크

| 리스크 | 설명 | 완화 |
|---|---|---|
| **WFB 데드라인** ★ | 3칩 page-full이 동시 도착 시 순차 처리로 마지막 칩이 지연. 단 최대 ~4.8ms ≪ 16ms 데드라인 | 단일 스레드 내부에서 **WFB(page-full) IRQ를 폴링보다 우선** 처리 |
| **버스 병렬성** (정정) | 병렬성은 스레드 수가 아니라 **"DMA가 CPU를 안 붙잡음 + 버스 2개"** 에서 나온다. 단일 스레드라도 유지 가능 — 아래 참고 | 비동기 kick(fire-and-collect) 구조로 짜면 SSP0∥SSP1 병렬 유지 |
| **우선순위 차등 상실** | M0=REALTIME 우선을 잃음 | M0 WFB를 스레드 내 최우선 서비스로 보전 |

**버스 병렬성 상세 (중요 — 스레드 수와 무관)**
`spiIO_DMA`는 DMA를 kick한 뒤 `os_evt_wait(0x10)`로 CPU를 양보한다. SSP0용·SSP1용 GPDMA 채널이 물리적으로 별개(`ssplib.c:181-185`)이므로, **M0 DMA 대기 중 스레드가 M1 DMA를 kick하면 두 버스가 하드웨어에서 동시 전송**된다. 병렬의 원천은 스레드 개수가 아니라 DMA+독립버스다.
- **단, 현재 `dma_read32n`→`spiIO_DMA`는 동기(blocking)** 구조("kick→완료대기→다음 kick")라, 그대로 단일 스레드로 옮기면 순차(M0 2.4ms + SSP1 4.8ms = 7.2ms)가 된다.
- **병렬을 실제로 얻으려면 비동기 kick(fire-and-collect)**: "M0·M1 kick을 먼저 하고 완료를 나중에 모아 대기" → SSP0(M0 2.4ms) ∥ SSP1(M1+M2 4.8ms) = **~4.8ms(SSP1 병목)**. 멀티스레드가 누리던 병렬을 락 없이 그대로 유지.
- SSP1 내부 M1↔M2는 같은 버스라 병렬 불가(순차 4.8ms) — 스레드 수 무관한 물리 제약.
- 구현 주의: `t_meter[chn]`·완료 세마포어를 채널별로 분리 관리(M0=chn0, M1=chn1). `t_meter[2]`가 이미 채널별이라 구조는 맞으나 `os_evt_wait`가 두 채널을 각각 대기하도록 재작성 필요(gems7100 `t_meter[chn]==0` 가드 참고).

### 16ms 예산 검증 (SSP 20MHz 기준)

- 칩당 WFB 버스트: 768워드 = 24,576비트 / 20MHz = 1.23ms(순수), 실측 오버헤드 포함 **~2.4ms** (`ssplib.c:209`)
- **3칩 WFB 순차 최악**: 3 × 2.4ms = **7.2ms** (예산의 45%)
- + 폴링(Energy/Power/RMS/THD 최악 몰림 ~1ms) = **~9~10ms < 16ms** (여유 ~6ms)
- **개별 칩 최대 지연** ~4.8ms ≪ 16ms 데드라인

→ **시간적으로 명확히 가능.** 리스크는 "총 시간 초과"가 아니라 "WFB를 폴링 뒤로 미루는 스케줄 실수"이며, 스레드 내 WFB 우선처리로 제거된다.

### SV300 vs gems7100 설계 대비

| | gems7100 | SV300 (현재) |
|---|---|---|
| 버스 배치 | M0=SSP0, M1=SSP1 (**미터별 전용**) | M0=SSP0, **M1·M2=SSP1 공유** |
| 동시성 처방 | **불필요**(미터별 전용 버스라 경합 자체가 없음, 락 없음) | **락으로 억제**(mutex/버스트락) — 버스 공유 탓 |
| `t_meter` | 최초 1회만 설정(덮어쓰기 금지) | 매번 덮어씀 |

- SV300은 M1·M2가 **SSP1을 공유**하므로 두 칩 WFB(각 2.4ms)가 반드시 순차 = SSP1에서 4.8ms 연속 점유. gems7100(전용 버스)보다 빡빡하나 여전히 16ms 내.
- **권장 절충안**: M0(SSP0)는 독립 유지, **M1+M2(SSP1)만 한 스레드로 통합**. 파형 손상 원인(M1↔M2 SSP1 커플링)을 정확히 겨냥하면서 M0 버스 병렬성·우선순위는 보전.

## 5.7. 실환경 파형 손상 진단 가이드

손상 **채널×양상**에 따라 원인이 갈린다:

| 채널 | 양상 | 유력 원인 |
|---|---|---|
| M0만 | 단일 스파이크 | flash/XIP 정지 커플링 (`g_sdBusy`, Quiet Capture 미흡). M0는 SSP1 락과 무관 |
| M1/M2만 | 단일 스파이크·THD 100% | SSP1 락 규약 위반 경로(§5.5 ③) 또는 26/09/10 버스트락 불충분 |
| 셋 다 | seam/불연속 | `re/fr` 동기화 또는 Wave_Task 알림 coalescing |
| 임의 | THD만 이상 | despike OFF(`WV_NO_DESPIKE`, `meter.h:10`)로 잔여 스파이크 미복구 |

- 파형은 **유일한 DMA 경로**(`dma_read32n`)이자 데드라인 빡빡 → 폴링과 다른 동시성 특성.
- 확정 계측: `readWFB_Data` 구간을 LED/타임스탬프로 재어 실제 버스트 시간과 3칩 위상차 확인(`ade9000.c:2038`에 LED 측정 흔적).

## 5.8. ADE9000 읽기 레지스터 버스트 가능 여부 (데이터시트 UG-1098 확정)

**결론: 흩어진 계측 레지스터는 버스트 불가. 버스트는 파형(WFB)만 가능하다.**

데이터시트 Table 19(p.46) + SPI Burst Read(p.47) 규정:

| 주소 범위 | 버스트 | 상세 |
|---|---|---|
| **0x000–0x4FF** (RMS/Power/Energy/THD/Angle 전부) | ❌ **불가** | BURST_EN=0이면 CRC 붙음, =1이면 **같은 데이터 반복**(주소 안 넘어감) |
| 0x500–0x63C, 0x680–0x6BC | ✅ | BURST_EN=1 필요, **+1 연속 증가만**(wrap) |
| **0x800–0xFFF (WFB 파형)** | ✅ | 기본 활성, `BURST_CHAN`으로 채널 스트리밍 |

**두 가지 결정적 사실:**
1. auto-increment는 **+1(연속)만** 지원하고 서브윈도우 끝에서 wrap. **+0x20/+0xa 같은 임의 stride 불가**.
2. 계측 레지스터(0x2xx)는 전부 **0x000–0x4FF라 애초에 버스트 영역이 아님**. 상 간격 +0x20(AVRMS 0x20D→BVRMS 0x22D→CVRMS 0x24D)은 절대 못 묶음.

**함의**: "ADE9000 r/w를 모두 DMA & burst로" 는 **하드웨어적으로 불가능**하다. 폴링 읽기(RMS/Power/Energy/THD)는 각각 독립 SPI 트랜잭션(16b 헤더+32b+CRC)으로 남을 수밖에 없다. 따라서 단일 스레드로 가도 **폴링은 폴링으로 유지**되며, 단일 스레드의 이득은 "DMA 버스트화"가 아니라 **동시 접근 제거(락·race 소멸)** 에서만 나온다. (§5.6 시간 계산은 폴링 유지 전제로 이미 맞음)

## 5.9. 데이터별 읽기 타이밍 제약 (one cycle / 10-12 cycle / energy)

각 데이터의 갱신 주기와 "놓쳤을 때" 결과. **energy만 destructive read라 진짜 엄격**하다.

**설정된 타이밍 파라미터**:
- `PWR_TIME=EGY_TIME=7999` (`ade9000.c:2318-2320`) → 8000샘플 = **1초** @8ksps
- `EP_CFG=(1<<4)|(1<<0)` = **RD_RST_EN(bit4)** + EGY_PWR_EN (`ade9000.c:2341`) → **에너지 read-with-reset 모드** ★

| 데이터 | STATUS0 | 주기 | 놓쳤을 때 | 데드라인 |
|---|---|---|---|---|
| **파형 WFB** | bit17 | **16ms** | 파형 torn(즉각 손상) | **엄격·최우선** |
| **Energy** | bit0 | 1s | **누적 손실**(읽기=리셋이라 destructive) | **엄격** |
| 10/12 RMS | bit20 | 200ms | 평균 윈도우 1개 누락 | 중간 |
| Power | bit18 | 1s | 값 1개 누락 | 중간 |
| FastRMS/Period | bit19 | ~8ms(반주기) | 반주기 스킵(무해) | 느슨 |
| THD | bit21 | ~2.6s | 값 유지 | 느슨 |
| Temp | bit25 | 느림 | 무관 | 최하 |

**핵심 — Energy의 destructive read**: `EP_CFG`의 RD_RST_EN=1이라 에너지 레지스터를 **읽으면 자동 0 리셋** 후 재누적. 즉 "읽기 = 이번 1초 구간 회수". 읽기를 놓치면 그 구간 누적이 소실되거나 다음 읽기에서 2초치가 뭉쳐 나온다. 그래서 `efr/ere` 더블버퍼(`ade9000.c:1179-1180`)로 받되 **readEnergy 자체는 1초 데드라인을 반드시 지켜야** 한다. 나머지 데이터는 non-destructive(레지스터가 최신값 유지)라 놓쳐도 다음 값을 읽으면 됨.

**단일 스레드 스케줄 우선순위**: **WFB(16ms) > Energy(1s, destructive) > 10/12RMS(200ms) > Power(1s) > FastRMS/THD/Temp**. WFB는 주기가 짧아 자주, Energy는 주기가 길어도 destructive라 절대 누락 금지. 한 인터럽트에 WFB+Energy+RMS가 동시에 떠도 2.4+0.3+0.3 ≈ 3ms로 16ms 내 처리 가능.

## 6. 요약

- **RTOS는 RTX** (`USE_RTX`). 소스의 `__FREERTOS` 블록은 죽은 코드. 신호는 RTX 이벤트 플래그(`os_evt_*`/`isr_evt_set`).
- **스택은 전 태스크 640워드 고정**(요청 stackSize 무시, `stack=NULL` 때문).
- **IRQ 구동형**: ISR은 `isr_evt_set(0x1, tid_meter[id])`로 태스크만 깨우고, 실제 SPI I/O는 전부 태스크 컨텍스트에서 수행.
- **파이프라인**: Meter → (evt 플래그) → Wave/Energy/RMSLog/PostScan → FFT 순으로 이벤트 플래그로 흐른다(§3.5).
- **버스 분리**: M0=SSP0 전용(REALTIME, 무락) / M1·M2=SSP1 공유(HIGH, `ssp1_mutex` 직렬화).
- **동시성 방어 3층**:
  1. 트랜잭션 단위 `ssp1_mutex` + CS(GPIO) 토글
  2. 파형 버스트 전체 SSP1 독점(2중 락 + `ssp1_burst` 재귀 회피)
  3. M1/M2 PQM 부하를 라운드로빈 + 슬라이스로 분산
- **STATUS0 조기 ack**로 파형 seam 방지.
- **CS는 소프트웨어 GPIO** 제어(M1/M2는 SSEL 핀먹스 미사용), 모두 락 구간 안에서 토글.
- 각 방어층은 실제 하드웨어 버그(스파이크·THD 100% 오계측)를 잡기 위해 진화한 결과다.
- **3-스레드 동시성(§5.5)**: 데이터 무결성은 현재 안전하나 **견고성은 취약**하다. benign data race 2건(`m12_pq_rr_owner`·`maxmin.fr` — race 존재하나 무결성 무영향) + **규약 의존 취약점(DMA setup: `spiIO_DMA`가 락 없이 `ssp1_mutex` 규약에만 의존, 위반 시 `t_meter[1]` 오배달·버스 손상)** + 가정 의존 2건(SSP1 락 불변식·FFT 단일스레드). 안전이 "코드 격리"가 아니라 "깨지기 쉬운 규약"에 기댄다.
- **단일 스레드 전환(§5.6)**: 위 취약점 대부분이 구조적으로 소멸. 16ms 예산 검증상 3칩 WFB 순차(~7.2ms)+폴링(~2ms)=9~10ms < 16ms로 시간 제약 만족. **버스 병렬성은 스레드 수가 아니라 DMA+독립버스에서 나오므로, 비동기 kick 구조로 짜면 단일 스레드라도 SSP0∥SSP1 병렬 유지**(순차 7.2ms→병렬 4.8ms). 권장은 M0 유지 + M1·M2(SSP1) 통합 절충안.
- **버스트 가능 여부(§5.8, 데이터시트 확정)**: 계측 레지스터(0x2xx)는 버스트 불가(0x000–0x4FF는 버스트 영역 아님, auto-inc는 +1만). **버스트는 WFB(0x800~)만 가능**. "전부 DMA" 는 하드웨어적으로 불가 — 폴링은 폴링으로 유지.
- **타이밍 제약(§5.9)**: energy만 **destructive read**(EP_CFG RD_RST_EN, 읽기=리셋)라 1초 데드라인 엄격. 파형은 16ms 엄격(torn). 나머지(RMS/Power/THD)는 non-destructive라 느슨. 단일스레드 우선순위 = WFB > Energy > 10/12RMS > 나머지.
- **실환경 파형 손상(§5.7)**: DMA setup 취약점·SSP1 버스트락(26/09/10 "실기 검증 필요")이 유력 후보. 파형은 유일한 DMA 경로이자 데드라인 빡빡.
