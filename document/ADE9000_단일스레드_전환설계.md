## 0. 설계 원칙 — "스레드를 SPI 버스 단위로 분리"

핵심 통찰: **동시성 경합의 단위는 칩이 아니라 SPI 버스**다. 현재 구조의 결함은 "스레드는 칩별(M0/M1/M2)인데, 칩들이 버스를 공유(M1·M2=SSP1)해서, 스레드가 버스 공유를 모른 채 동시 접근"하는 불일치다. **스레드를 버스 단위로 재정렬하면 "한 버스 = 한 스레드"가 되어 락이 원천 불필요**해지고, 서로 다른 버스는 병렬해도 안전하다.

| 분할 방식 | 스레드 | 락 | 버스 병렬 | 판정 |
|---|---|---|---|---|
| **현재 (칩별)** | M0, M1, M2 (3) | ✅ 필요(M1·M2 SSP1 공유) | O | 손상 원인 |
| **버스별 (안 A, 권장)** | M0=SSP0, **M12=SSP1** (2) | ❌ 불필요 | O(자연) | **최적** |
| **완전 단일 (안 B)** | All (1) | ❌ 불필요 | 비동기 kick 필요(§7) | 병렬 이득 상실 위험 |

### 두 가지 안

| | **안 A (권장): 버스별 분리** | 안 B: 완전 단일 |
|---|---|---|
| 미터 스레드 | Meter0(SSP0, 유지) + **Meter12(SSP1, 신설)** = 2개 | **MeterAll** 1개 |
| 겨냥 | M1↔M2 SSP1 커플링(손상 주범) 정확히 제거 | 모든 동시성 제거 |
| M0 REALTIME 우선순위 | **유지** | 상실 |
| SSP0∥SSP1 병렬 | **자연히 유지** | 비동기 kick 필요(§7) |
| WFB 데드라인 리스크 | 낮음(M0 독립) | 중간(3칩 순차, 완화 필요) |
| 변경 규모 | 중 | 큼 |
| 리스크 | **낮음** | 중 |

> **버스가 2개(SSP0/SSP1)인 이 하드웨어에서는 "버스별 2스레드"가 자연스러운 최적점**이다. 완전 단일(안 B)은 두 버스를 한 스레드가 번갈아 써서 병렬을 잃으므로(비동기 kick으로 복구는 가능하나 복잡), 특별한 이유가 없으면 안 A.
> 참고(코드 확정): gems7100은 ADE9000 최대 2개를 **미터별 전용 버스**(M0=SSP0, M1=SSP1, 칩:버스 1:1)로 처리, 듀얼 시 Meter 스레드 2개·단일 시 1개. **버스 전용이라 경합 없음 → SSP 락 없음**. gems7100의 Wave 통합(de56f36)은 소비 단순화지 동시성 처방 아님. SV300은 3칩/2버스라 M1·M2가 SSP1 공유 → gems7100식 "칩당 전용 버스"가 HW상 불가 → **버스별 스레드 분리(M0=SSP0, M12=SSP1)가 필요**. ✅ **사용자 확정: 버스별 스레드로 처리.**

> **본 설계서는 안 A(버스별 분리)를 기준으로 작성.** 안 B는 §9에 차이만 별도 기술.
> ❓ **결정 필요 사항 1: 안 A / 안 B 중 선택.**

## 2. 파일별 상세 수정

### 2-1. `src/meter.c` — 스레드 통합

**삭제**: `Meter1_Task`(5280), `Meter2_Task`(5312).

**신설**: `Meter12_Task` — M1·M2 IRQ를 한 스레드가 순차 서비스.

```c
void Meter12_Task(void *param) {
    // --- 초기화: 기존 Meter1/2_Task의 init을 순차로 ---
    for (int id = 1; id < ACTIVE_METER_CH_COUNT; id++) {   // id=1,2
        memset(&wQ[id], 0, sizeof(wQ[id]));
        wbFFT8k[id].fr = wbFFT8k[id].re = 0;
        initADE9000(id);
        while (!getAdeStatus(id)->online) { osDelayTask(5000); initADE9000(id); }
    }
    ExtINTR_Init(1, 2, 0); ExtINTR_Enable(1);   // M1: PINT1/EINT2
#ifdef CH3
    ExtINTR_Init(2, 3, 0); ExtINTR_Enable(2);   // M2: PINT2/EINT3
#endif
    _enableTaskMonitor(Tid_Meter2, 50);

    // --- 루프: 두 칩 순차 스캔 (단일 meter_scan) ---
    while (1) {
        meter[0].cntl.wdtTbl[Tid_Meter2].count++;
        os_evt_wait_or(0x3, METER_SCAN2_ZX_TMO_MS);   // 0x1=M1, 0x2=M2 (§3 방법1)
        os_evt_clr(0x3, tid_meter[1]);
        meter_scan(1);          // ← meter_scan_2 폐지, 통합 meter_scan(id)
#ifdef CH3
        meter_scan(2);
#endif
    }
}
```

> ⚠️ **초기화 순서 주의**: 기존 M1/M2 태스크가 각자 하던 `initADE9000`을 한 스레드가 순차로 함. 문제없음(각 칩 CS 분리). 단 `initPQHeader`는 이미 Meter0에서 전 채널 직렬 호출(`meter.c:5262`)하므로 **여기서 중복 호출 금지**.

> ✅ **결정 2 확정: 옵션 A (항상 둘 다 호출)**. Meter12 루프에서 `meter_scan(1)`·`meter_scan(2)`를 매번 순차 호출. 빈 스캔 낭비(STATUS 읽기 수µs)는 미미하고, IRQ 구분 로직이 불필요해 버그 여지가 적음(한 칩 IRQ를 놓쳐도 다른 칩 깨움에 묻어 처리). 먼저 A로 구현·검증 후 필요 시 최적화(pending만)로 전환.

### 2-2. `src/ade9000.c` — meter_scan / meter_scan_2 → **단일 `meter_scan(id)` 통합** ★

**결정: 두 함수를 합친다.** 두 함수의 실질 차이는 3가지뿐이고 전부 id로 파라미터화 가능. 특히 `meter_scan_2`의 존재 이유였던 RR+슬라이스는 **버스별 분리로 삭제되므로 차이가 자연 소멸**한다.

| 차이 | meter_scan(M0) | meter_scan_2(M1/M2) | 통합 처리 |
|---|---|---|---|
| ZX 타임아웃 | 20ms | 50ms | `id==0 ? 20 : 50` |
| PQM 부하분산 | 없음 | RR+슬라이스 | **삭제**(버스별 분리로 불필요) → 차이 소멸 |
| LED 토글 | `Board_LED_Toggle`(bit0) | 없음 | `if(id==0)` |
| 나머지 전부 | **완전 동일** | **완전 동일** | 그대로 |

```c
void meter_scan(uint8_t id) {          // 단일 함수, 전 채널(0/1/2) 처리
    uint16_t tmo = (id == 0) ? 20 : METER_SCAN2_ZX_TMO_MS;
    if (id >= METER_CH_COUNT) return;
    if (os_evt_wait_and(0x1, tmo) == OS_R_TMO) { ... }   // (Meter12는 루프에서 이미 wait → 구조 조정, §주)
    read_reg32(id, AD9X_STATUS0, &stat0); read_reg32(id, AD9X_STATUS1, &stat1);
    write_reg32(id, AD9X_STATUS0, &stat0);               // 조기 ack
    if (stat0 & (1<<0))  { readEnergy(id); if (id==0) Board_LED_Toggle(LED_STS); }
    if (stat0 & (1<<17)) readWFB_Data(id);
    if (stat0 & (1<<19)) { readPeriod(id); readPhaseFastRMS(id); checkPqEvent(id); }  // RR/슬라이스 없이 매번
    if (stat0 & (1<<20)) readRmsAngle(id);
    if (stat0 & (1<<18)) readPhasePower(id);
    if (stat0 & (1<<21)) readPhaseTHD(id);
    if (stat0 & (1<<25)) readTemp(id);
    // ZX 카운트 / clearEventList / STATUS1 ack / wCalF — 기존과 동일(양쪽이 이미 동일 코드)
}
```

- **삭제**: `meter_scan_2` 함수, `m12_pq_rr_owner`(2764), `m12_pq_slice[]`(2762), RR+슬라이스 분기(2820-2843).
- **주의(ZX 대기 위치)**: 현재 `meter_scan`/`meter_scan_2`는 함수 진입부에서 `os_evt_wait`를 한다. Meter12는 루프에서 두 칩을 순차 스캔하므로, **ZX 대기를 함수 안이 아니라 Meter12 루프에서 1회**만 하도록 구조 조정 필요(위 §2-1 루프의 `os_evt_wait_or`). M0(Meter0_Task)는 기존처럼 함수 내 wait 유지 가능 — 또는 대기를 태스크 루프로 빼서 통일. → **결정3(IRQ 구분)과 함께 확정.**

**`meterIrqSvc`**(2412): 통보 대상 변경.

## 3. IRQ 구분 방법 — 방법1 vs 방법2

M1·M2 두 IRQ를 한 스레드가 구분해 받아야 함.

**방법1 (이벤트 플래그 분리)** — 위 예시. M1→0x1, M2→0x2. `os_evt_wait_or(0x3)`.
- 장점: 어느 칩 IRQ인지 명확. 단점: 플래그 비트 2개 소비.

**방법2 (pending 폴링)** — ISR은 `irqPending[id]=1`만 세우고 단일 이벤트로 깨움. 태스크는 pending 칩 순회.
- 장점: 소비자 태스크 패턴(per-id 폴링)과 일관, 확장 용이. 단점: pending 배열 신설.

> ❓ **결정 필요 사항 3: 방법1 / 방법2.** (권장: 방법1 — 변경 최소)

## 5.5. 버스별 분리 시 DMA setup 함수(`spiIO_DMA`) 보호 검토

핵심 질문: 버스별 분리(M0=chn0, M12=chn1)를 해도 `spiIO_DMA`·`Chip_GPDMA_Transfer`는 **두 스레드가 공유하는 코드**다. 락이 필요한가?

**답: `spiIO_DMA` 자체에 락은 불필요. 단 GPDMA 전역 레지스터 1곳(DMAMUX)만 이론적 경합점.**

`spiIO_DMA`(`ssplib.c:240`)·`Chip_GPDMA_Transfer`(`gpdma_18xx_43xx.c:603`)가 건드리는 자원 분석:

| 자원 | 인덱싱 | 판정 |
|---|---|---|
| `t_meter[chn]`, `isDma*[chn]`, `dmaChTx/Rx[chn]` | chn(버스)별 | ✅ M0(0)↔M12(1) 격리 |
| `pGPDMA->CH[ch]`(SRC/DEST/CONFIG/CONTROL) | 채널별 | ✅ 격리 |
| SSP FIFO, `Chip_SSP_DMA_Enable(pSSP)` | pSSP별 | ✅ 격리 |
| `pGPDMA->INTTCCLEAR/INTERRCLR = (1<<ch)` | write-1-clear | ✅ 채널비트만 씀, 무해 |
| `pGPDMA->CONFIG = E` | 컨트롤러 enable | ✅ 멱등(idempotent) |
| **`LPC_CREG->DMAMUX` RMW** (`gpdma:308-310`) | **컨트롤러 전역, 비원자 RMW** | ⚠️ **이론상 경합** |

**유일 경합점 — DMAMUX**: `configDMAMux`가 `temp = DMAMUX & ~mask; DMAMUX = temp | (func<<shift);` 로 **비원자 RMW**. M0는 ch9/10(SSP0), M12는 ch11/12(SSP1) 비트를 건드려 필드는 안 겹치나, read→write 사이 선점 시 상대 필드 롤백 가능.
- **실질 위험 낮음**: DMAMUX는 채널→기능 매핑으로 **부팅 후 고정값**. 매 전송이 같은 값을 재기록하므로 롤백돼도 다음 전송에서 복원.

**권장 처방** (택1, 락 불필요):
1. **(권장) DMAMUX 설정을 부팅 1회로 분리** — `Board_DMA_Init`에서 SSP0/SSP1 채널 mux를 1회 설정하고, 매 전송 경로(`Chip_GPDMA_Transfer`→`configDMAMux`)에서 재설정 안 하게. → 전역 RMW 경합 원천 소멸, 가장 깨끗.
2. **(최소변경) 그대로 수용** — DMAMUX가 고정값 재기록이라 실질 무해. 문서에 근거 명시하고 유지.

> **결론**: 버스별 분리 후 `ssp1_mutex`를 제거해도 DMA setup은 채널 격리로 안전하다. `spiIO_DMA`에 새 락을 씌울 필요 없음. DMAMUX만 처방 1로 정리하면 완전 무결.
> ❓ **결정 필요 사항 5: DMAMUX 처방 1(부팅 1회 분리) / 2(현행 수용).**

## 5.6. Meter 스레드 블로킹 요소 및 FS 위임 재설계 (★ 최우선)

**사용자 경험: FS 호출이 병목의 주범.** 전수 조사 결과, 문제의 실체가 명확하다.

### 좋은 소식 — 메인 경로(매 인터럽트)는 이미 깨끗

`meter_scan`/`meter_scan_2`의 **read 함수들(readEnergy/WFB/Period/FastRMS/RmsAngle/Power/THD/Temp)은 읽어서 per-id 버퍼에 넣고 신호만** 보낸다. 무거운 계산(sqrt/cos/atan2/FFT)·품질로그·EN50160 파일쓰기는 **이미 PostScan/Energy/RMSLog/FFT 스레드로 위임**돼 있다. 결정하신 "현행 per-id 더블버퍼 유지"와 정확히 맞물린다. → **메인 read 경로에는 fopen/fwrite/putFsQ 없음.**

### 나쁜 소식 — 유일한 FS 병목: `checkPqEvent`→`pushEvent`가 Meter 안에 있다 ★

PQ 이벤트(sag/swell/OC/interruption) **종료 시점**에 Meter 스레드가 직접:
- `pushEvent`(`meter.c:4628`) 호출 지점: `ade9000.c:2607`(SAG), `:2622/2628`(INTR), `:2681`(SWELL), `:2734`(OC)
- 그 안에서: **`putFsQ` 2회**(`meter.c:4704,4712`) + `sprintf` 2회 + `fetchEvent`/`fetchItic`/`fetchItic2` O(N) 스캔 + **블로킹 `printf`**

**`putFsQ`는 FS 큐 full 시 `osDelayTask(5)`×최대 200회 = 최대 1초 블록**(`meter.c:144-156`). FS_task가 SPI-NOR flash write(느림)로 밀리면 큐가 차고, **이벤트 발생 순간 Meter가 최대 1초 정지 → WFB 16ms 데드라인 완전 상실**. 이벤트 폭주 시 파형 손상과 직결 가능.

### 블로킹 요소 전수표

| # | 위치 | 분류 | 경로 | 블록 |
|---|---|---|---|---|
| 1 | `checkPqEvent`→`pushEvent` (`ade9000.c:2607~2734`) | **FS 큐잉+sprintf+fetch+printf** | 조건부(이벤트) | **putFsQ full 시 최대 1s** ★ |
| 2 | `putFsQ` full 스핀 (`meter.c:144-156`) | 큐 full 대기 | 조건부 | 최대 1s |
| 3 | printf 다수 (`debug.c:167` 스핀) | UART 블록 | 조건부(이벤트/타임아웃) | 라인당 3.5~5ms |
| 4 | `readWFB_Data` despike (`ade9000.c:2088~2126`) | 정수 6×128 루프+보간 | **메인(page-full)** | 수백µs~ms (현재 `WV_NO_DESPIKE`로 OFF) |
| 5 | `ssp1WfbLock` 버스트 독점 (`ssplib.c:218`) | mutex | 메인(M1/M2) | 상대 ~2.4ms — **버스별 분리로 소멸** |
| 6 | `ssp1_mutex` 매 트랜잭션 (`ssplib.c:585`등) | mutex 무한대기 | 메인(M1/M2) | 상대 점유분 — **버스별 분리로 소멸** |
| 7 | `spiIO_DMA` 완료 대기 (`ssplib.c:298`) | DMA 완료 | 메인(WFB) | 정상 ~ms, 최대 100ms(정상 동작) |
| 8 | `spiIO8_Polling` 바이트 스핀 (`ssplib.c:362`) | HW 스핀 | 메인(레지스터 R/W) | 트랜잭션당 수~수십µs(불가피) |

> #5·#6은 **버스별 분리(안 A)로 자동 소멸**. #7·#8은 SPI 하드웨어 대기라 정상. #4는 이미 OFF. **실질 위험은 #1·#2(FS)와 #3(printf).**

### 재설계 원칙 — Meter는 FS·printf를 절대 직접 하지 않는다

```
[현재]  Meter ─(이벤트 종료)→ checkPqEvent → pushEvent → putFsQ(최대1s블록)+printf
[재설계] Meter ─(이벤트 감지·마킹만)→ per-id 이벤트큐(RAM, non-block) ─신호→ 이벤트처리 스레드 → pushEvent/FS/printf
```

- Meter가 하는 일 = ①SPI 읽기 ②per-id 버퍼 쓰기 ③**이벤트 감지 + RAM 큐 마킹**(fast RMS 비교는 가벼움) ④신호. **끝.**
- `pushEvent`·`fetchEvent`·`putFsQ`·`printf`는 **후단 스레드(PostScan 또는 신설 PqEvt_Task)로 이관**.
- 이렇게 하면 FS 병목(#1·#2)이 Meter 경로에서 **완전 제거**되고, FS 지연은 후단 스레드와 FS_task 사이에만 국한.

### 부수 개선 (선택)

- **`putFsQ` non-blocking화**: 큐 full 시 `osDelayTask` 대신 즉시 drop + 유실 카운터. 어느 스레드도 FS 큐 때문에 블록 안 됨(단 유실 로그 필요).
- **printf를 Meter 경로에서 제거**: 이벤트 로그 printf를 후단으로 이관하거나 링버퍼 로거로.
- **flash write 배칭 / XIP 회피**: FS 병목의 근본은 SPI-NOR write 속도(`g_sdBusy` XIP 정지가 M0 파형까지 교란). FS_task write를 모아 쓰거나 타이밍 조정 — 별도 과제.

> ❓ **결정 필요 사항 6**: 이벤트 처리(pushEvent 계열)를 **기존 PostScan_Task에 위임 / 신설 PqEvt_Task에 위임** 중 선택.
> ❓ **결정 필요 사항 7**: `putFsQ` non-blocking화(drop+카운터) 적용 여부.

## 6.5. 이벤트 처리 위임 설계 (결정 6 = 신설 PqEvt_Task 확정)

**결정: 이벤트 처리를 신설 스레드로 위임 + one cycle(반주기) fast RMS를 그 스레드에 공급.**

### 구조

```
[Meter 스레드] readPhaseFastRMS (bit19, 반주기 ~8ms)
   ├─ ade9000[id].urmsFast/irmsFast SPI 읽기
   ├─ fastRmsQ[id] 링버퍼에 (urmsFast[3],irmsFast[3],ts) push   ← 신규 공급
   ├─ rmsWin[id] 링(RMSLog용) push (기존 유지)
   └─ 신호 → PqEvt_Task
[PqEvt_Task (신설)] — 큐 소비하며:
   ├─ checkPqEvent 로직(sag/swell/OC 판정 상태머신)   ← Meter에서 이동
   └─ 이벤트 발생 시 pushEvent/putFsQ/printf   ← FS 병목 여기 격리
```

**효과**: FS 병목(putFsQ 최대 1s)과 이벤트 printf가 Meter 경로에서 **완전 제거**. Meter는 "fast RMS 읽어 큐에 넣고 신호"만.

### fast RMS 공급 = 전용 링버퍼 (스냅샷)

sag/swell/interruption 판정은 **모든 반주기 값**을 봐야 정확(깊이·복귀 추적)하므로 "현재값+신호"가 아니라 **per-id 링버퍼**로 공급(기존 `rmsWin` 패턴과 동일). 이벤트 스레드가 밀려도 반주기 값을 안 놓침.

### 상태 소유권 (경합 검증)

| 상태 | writer | PqEvt 접근 | 판정 |
|---|---|---|---|
| `urmsFast[]`/`irmsFast[]` | Meter | 링버퍼 **스냅샷 복사**본 | ✅ 경합 없음 |
| `cntl.online` | **Meter(ZX 처리)만 write** | read only | ✅ 단일 writer(워드 원자적) |
| `cntl.zxMonCnt` | Meter만 write | read only | ✅ 동일 |
| `cntl.sagSt`/`pqe`/`sagMask`/상태머신 | checkPqEvent 전용 | **PqEvt 단독 소유로 이동** | ✅ 오히려 격리↑ |
| `sagLevel`/`swellLevel` | 설정 시 계산 | read only | ✅ 설정값 |

> `online`/`zxMonCnt`는 Meter가 유일 writer·PqEvt는 reader → 단일 writer 패턴이라 안전. sag 상태머신 전체는 PqEvt 단독 소유가 되어 더 깨끗. → **위임 안전.**

## 6.6. 멀티스레드 우선순위 재검토 (재설계 기준)

### 현재 우선순위의 문제

1. **계측 < 소비 역전**: `wave(HHIGH+5) > meter1/2(HIGH+4)`. WFB 데드라인상 **계측(WFB 읽기)이 소비(wave 처리)보다 우선**이어야 하는데 M1/M2가 wave보다 낮다.
2. **LED가 HHIGH(+5)** (WDT clear용, 26/03-11): 계측·wave와 동급이라 방해 소지.
3. 신설 스레드(Meter12, PqEvt) 배치 미정.

### 권장 우선순위 (재설계)

| 태스크 | 현재 | **권장** | 근거 |
|---|---|---|---|
| **Meter0 (M0/SSP0)** | REALTIME(+6) | **REALTIME(+6)** | WFB 16ms 데드라인, 최우선 |
| **Meter12 (M1·M2/SSP1)** | HIGH(+4) | **REALTIME(+6) 동급 or HHIGH(+5)** ↑ | 동일 WFB 데드라인. wave보다 위 |
| wave | HHIGH(+5) | **HIGH(+4)** ↓ | 소비 < 계측 |
| rmslog/post/energy | HIGH(+4) | HIGH(+4) | 계산·로그 |
| LED(WDT) | HHIGH(+5) | **HIGH(+4)** ↓ 또는 경량화 | 계측 방해 방지 |
| **PqEvt (신설)** | — | **NORMAL(+3)~LOW(+2)** | FS 물림·데드라인 느슨 → 계측·소비 방해 금지 |
| cmd/통신 | NORMAL(+3) | NORMAL(+3) | |
| FS/trend/iom | LOW(+2) | LOW(+2) | |
| fft/shell | LLOW(+1) | LLOW(+1) | |

### 원칙: **계측(WFB) > 소비 > 이벤트/FS**

- Meter0·Meter12(REALTIME/HHIGH) > wave/rmslog/post/energy(HIGH) > PqEvt/cmd(NORMAL) > FS/trend(LOW) > fft/shell(LLOW)
- **Meter0=Meter12 동급 REALTIME 권장**: 버스가 달라(SSP0/SSP1) 서로 선점해도 안전. RTX 라운드로빈 OFF라 둘은 blocking(DMA대기)에서만 양보 → **WFB DMA 대기 중 상대 실행 = SSP0∥SSP1 버스 병렬 자연 성립.**
- **PqEvt는 낮게**: FS 병목을 유발하므로 계측·소비를 방해하면 안 됨. 이벤트 데드라인 느슨(sag/swell 수십ms~s).

### 검증 필요

- Meter12 REALTIME 상향이 **이더넷 인터럽트 프레임과의 상호작용**에 미치는 영향(README 26/08/10 "웹 이더넷 프레임+meter_scan_2 PQM 스택초과" 이력) — 실기 검증.
- LED WDT clear 경로를 우선순위 낮춰도 WDT 안 물리는지 확인.

> ❓ **결정 필요 사항 3(재확정)**: 결정2=옵션A(둘 다 호출)이므로 IRQ 구분 불필요 → **M1·M2 모두 단일 플래그(0x1)로 tid_meter[1] 깨움** 권장(0x1/0x2 분리·pending 배열 불요).
> ❓ **결정 필요 사항 8(신규)**: Meter12 우선순위 = **REALTIME 동급 / HHIGH** 중.

## 7. (안 B 전용) 비동기 kick으로 버스 병렬 유지

완전 단일(안 B) 선택 시에만 해당. 순차 blocking이면 M0+M1+M2 = 7.2ms.
버스 병렬(SSP0∥SSP1)을 살리려면 `spiIO_DMA`를 **fire-and-collect**로 분리:
- `spiIO_DMA_start(chn)`: kick만(대기 안 함)
- `spiIO_DMA_wait(chn)`: `os_evt_wait(0x10)` 완료 수거
- M0(chn0)·M1(chn1) 동시 kick → 각각 wait → SSP0∥SSP1 병렬(~4.8ms)
- `t_meter[chn]`·완료 세마포어 채널별 정확 분리 필수(gems7100 `t_meter[chn]==0` 가드 참고)

> 안 A에서는 M0가 이미 독립 스레드라 이 작업 **불필요**.

## 10. 리팩토링 목표 구조 (실제 구현 기준)

기존 함수 최소수정이 아니라 **깨끗한 계층·역할 분리**를 목표로 한다.

### 스레드 최종 구성

| 스레드 | 우선순위 | 역할(오직 이것만) |
|---|---|---|
| **Meter0** | REALTIME | SSP0(M0) — `meter_scan(0)`: STATUS 읽고 read함수 호출, per-id 버퍼 write, 신호. FS·printf·무거운 연산 없음 |
| **Meter12** | REALTIME/HHIGH | SSP1(M1·M2) — `meter_scan(1)`·`meter_scan(2)` 순차 |
| **PqEvt** (신설) | NORMAL~LOW | fast RMS 링 소비 → sag/swell/OC 판정 → pushEvent/FS/printf (FS 병목 격리) |
| Wave | HIGH | 파형 소비 → FFT 신호 |
| RMSLog/PostScan/Energy | HIGH | 계산·로그 (기존) |
| FFT | LLOW | 고조파 |
| FS_task | LOW | flash I/O (putFsQ 소비) |

### 역할 원칙 (계층)

```
계층1 SPI I/O (Meter0/Meter12): ADE9000 읽기/쓰기 + per-id 버퍼 write + 신호. 끝.
계층2 연산    (PostScan/Energy/RMSLog/FFT): per-id 버퍼 읽어 계산. SPI 접근 안 함.
계층3 이벤트  (PqEvt): fast RMS 링 소비 → 판정 → 이벤트/FS.
계층4 저장    (FS_task): putFsQ 소비, flash write. 다른 계층은 putFsQ에 절대 블록 안 됨.
```

- **계측 스레드는 FS·printf 금지** (제1 제약)
- `meter_scan(id)` 단일 함수, RR/슬라이스/락 없음
- `checkPqEvent`는 Meter에서 제거 → PqEvt로 이동, fast RMS는 `fastRmsQ[id]` 링으로 공급
- `putFsQ` non-blocking화(큐 full 시 drop+카운터) — 어느 계층도 FS에 블록 안 됨

### 삭제/신설 총괄

- **삭제**: `meter_scan_2`, `Meter1_Task`, `Meter2_Task`, `ssp1_mutex`/`ssp1_wfb_mutex`/`ssp1_burst`, `ssp1WfbLock/Unlock`, `m12_pq_rr_owner`, `m12_pq_slice[]`, 모든 `if(bus==1) osAcquireMutex`
- **신설**: `Meter12_Task`, `PqEvt_Task`, `fastRmsQ[]` 링버퍼
- **이동**: `checkPqEvent`(+pushEvent 계열) Meter→PqEvt
- **통합**: `meter_scan`+`meter_scan_2`→`meter_scan(id)`
- **정리**: `DMAMUX` 부팅 1회 분리, `putFsQ` non-block, 우선순위 재배치

## 11. 작업 분할 계획 (에이전트 위임 + 감독·통합)

> **커밋은 새 분기에.** main 직접 금지. 각 단계 독립 커밋으로 롤백 용이.

수정 규모가 크므로 **독립 가능한 단위로 에이전트에 분할 위임**하고, 감독자가 통합·빌드 검증한다. **의존성 순서**로 직렬화(앞 단계가 뒤 단계 전제):

| 단계 | 작업 | 의존 | 위임 단위 |
|---|---|---|---|
| **W1** | `meter_scan`+`meter_scan_2` → 단일 `meter_scan(id)` 통합 (RR/슬라이스 제거) | — | 에이전트 1 |
| **W2** | `ssp1_mutex`/`wfb_mutex`/`burst`/`ssp1WfbLock` 제거, `if(bus==1)` 락 삭제 | W1 | 에이전트 2 |
| **W3** | `Meter1/2_Task`→`Meter12_Task` 통합, app_main 태스크 생성 수정, IRQ 통보 단일화 | W1 | 에이전트 3 |
| **W4** | `checkPqEvent`+pushEvent를 PqEvt_Task로 이동, `fastRmsQ[]` 링 신설, Meter는 공급만 | W3 | 에이전트 4 |
| **W5** | `putFsQ` non-blocking화 + DMAMUX 부팅1회 분리 + 우선순위 재배치 | W2,W4 | 에이전트 5 |

- 각 단계 후 **감독자가 빌드/컴파일 확인**, 커밋. 실기 검증은 사용자.
- W1·W2는 순차(락 제거는 통합 후), W3는 W1 후 병렬 가능, W4는 W3 후, W5는 마지막.
- 각 에이전트에 **§10 목표 구조 + 해당 단계 범위만** 명확히 전달. 범위 밖 파일 수정 금지 지시.

## 결정 요청 요약

1. **분할 축** — ✅ **버스별(안 A) 확정**
2. **Meter12 스캔** — ✅ **옵션 A(둘 다 호출) 확정**
3. **IRQ 구분** — 옵션A이므로 **단일 플래그(0x1) 통합 권장**(0x1/0x2 분리 불요)
4. **SSP1 단독 접근** — ✅ **확인 완료: 안전**(락 제거 가능)
5. **DMAMUX 처방** — 1(부팅 1회 분리, 권장) / 2(현행 수용)
6. **이벤트 처리 위임** — ✅ **신설 PqEvt_Task 확정** + fast RMS 링 공급
7. **`putFsQ` non-blocking화** — 적용 권장(FS 병목 근본 차단)
8. **Meter12 우선순위** — REALTIME 동급 / HHIGH

**남은 결정: 3(단일플래그 확인)·5(DMAMUX)·7(putFsQ)·8(Meter12 우선순위).** 확정 후 새 분기 생성 → W1~W5 에이전트 위임·통합 착수.

데이터 전달 = **현행 per-id 더블버퍼+이벤트플래그 유지**(확정).
위 확정 후 브랜치 생성 → 커밋 단위(①이벤트처리 위임=FS 병목 제거 → ②버스별 스레드 통합 → ③부하분산·락 제거)로 작업 착수.
※ 커밋 순서 변경: **FS 병목 제거(①)를 최우선**으로 — 사용자 경험상 가장 큰 병목이고, 스레드 통합과 독립적으로 먼저 검증 가능.
